# Repo Sense Product Detailed Requirements

This document captures the detailed product vision for Repo Sense, including the full Pillar / Capability / Topic taxonomy, prompt ground rules, and the product-level requirements needed to envision the platform.

## Purpose

* Describe the product in detail, beyond the high-level concept.
* Define the assessment taxonomy, page model, and prompt-quality rules.
* Preserve the operational ground rules for prompt content and assessment output.
* Bridge product design with the implementation requirements in sub-documents.

## Product scope

Repo Sense should support:

* high-level product vision and catalog navigation,
* structured assessment taxonomy with Pillars, Capabilities, and Topics,
* prompt modules with metadata and automation guidance,
* exportable assessment manifests,
* report generation and score aggregation,
* advisory disclaimers and content-grounding rules.
* launch-focused MVP support for Security and Observability.
* GitHub Pages-compatible static site delivery.
* repository-native prompt storage and organization.

## Pillar / Capability / Topic model

### Abilities

We use the term `abilities` as a generic umbrella for the assessment units defined by Pillars, Capabilities, and Topics.
This makes it easier to speak about changes, updates, or summaries that apply across the taxonomy.

### Pillars

Pillars are the highest-level assessment domains. Each Pillar represents a strategic area of repository health and governance.

Example Pillars:

* Security
* Observability
* Documentation
* DevOps
* API Strategy
* Developer Experience
* Reliability
* Maintainability
* Performance
* Scalability
* Testing
* Compliance
* Version Control
* AI Slop
* Configuration
* Errors
* Language & Framework Best Practices

### Capabilities

Capabilities are grouped assessment areas inside a Pillar. They describe the specific scope of the assessment within that domain.

Examples:

* Security → Secret Management, Dependency Auditing, Architectural Anti-patterns, Data Privacy, Access Control, Injection Prevention
* Observability → Metrics, Tracing, Logging, Alerting
* Documentation → README, ADRs, API Specs, Code-Level Docs
* DevOps → CI/CD, Infrastructure as Code, Environment Parity

### Topics

Topics are individual sub-items within a Capability. They represent a concrete check, prompt, or question set that can be exported and executed.

Examples:

* Secret Management → Hardcoded credential detection, `.env` leak detection, secret rotation policy
* Dependency Auditing → CVE scanning, license compliance, dependency drift
* Documentation → architecture overview, onboarding clarity, API spec validity
* Testing → unit coverage, integration paths, regression suite health

## Product detail expectations

* Each Pillar should have a dedicated landing page.
* Each Capability should have a dedicated detail page under its Pillar.
* Each Topic should be surfaced as a specific assessment item with examples and prompts.
* Prompt pages should be linked to the Pillar / Capability / Topic taxonomy.
* Collectives should be groupings of multiple Pillars or Capabilities for common workflows.

## Prompt ground rules

Every prompt and prompt module must follow these ground rules:

* No edit policy: Prompts may assess and recommend, but they must never instruct the AI to modify or generate code directly.
* Data privacy: Prompts must avoid requesting or retaining PII, credentials, secrets, or proprietary data.
* Attribution: Findings should include file paths, relevant line numbers, and evidence references where possible.
* Confidence taxonomy: Prompts should require the AI to distinguish between confirmed issues and likely observations.
* No hallucination: Prompts must explicitly instruct the AI to label uncertain findings as "Potential" or "Needs verification."
* Scope discipline: Each prompt should target a clearly defined Topic and avoid broad, unfocused checks.
* Reusability: Prompts should be modular so they can be reused across related Capabilities and Topics.

## Prompt metadata and taxonomy

Each prompt module should be captured with standardized metadata:

* name
* description
* pillar
* capability
* topic
* applicable languages/frameworks
* use cases
* automation guidance
* impact
* confidence/evidence requirements
* best practices
* related prompts
* tags

## Prompt repository organization

Prompt assets should be stored in Git and organized as code.

* Create a nested folder structure keyed by Pillar, Capability, and Topic.
* Each item folder may contain:
  * prompt metadata file (YAML/JSON/frontmatter Markdown)
  * prompt body content
  * assets such as images or diagrams in an `images/` subfolder
  * supporting files, templates, or sample output expectations
* This file-based approach enables version control, review workflow, and GitHub Pages compatibility.

## Report and manifest expectations

* Root manifests should orchestrate prompt execution and provide a high-level assessment persona.
* Reports should support hierarchical scoring by Topic → Capability → Pillar.
* Reports should include Executive Summary, Detailed Findings, and General Observations.
* Reports should produce structured output that can be rendered as JSON, Markdown, or HTML.

## Product design notes

* The product should be envisioned as a marketplace of assessment modules, not a one-size-fits-all scanner.
* Users should be able to choose verticals, sub-verticals, or entire collectives.
* The platform should present taxonomy and prompt selection clearly so users understand what they are getting.
